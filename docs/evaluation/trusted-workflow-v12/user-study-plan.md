# 目标用户研究方案（P3 · **只准备，未执行**）

> ⚠️ 本文件只包含招募脚本、任务脚本、观察记录模板。**没有招募到任何真实用户，没有跑过任何一场。**
> 在任何对外材料里，不得把本文件当作「用户验证已完成」的证据。

## 一、要回答的三个问题

本轮改版的核心主张是「针对一个真实岗位，拿到一份事实可核对、版本可辨认的投递简历，并用真正投出去的那一版准备面试」。用户研究要验证的是：

1. **事实可核对性**：用户能不能看懂「哪些是已经核对过的、哪些还没有」？会不会误以为系统已经帮他确认过？
2. **版本可辨认性**：用户能不能分清「草稿」和「正式投递版」？面试准备时会不会拿错版本？
3. **多岗位不串味**：改了一个岗位的事实后，用户是否预期其它岗位跟着变？提示是否足够？

## 二、样本

| 项 | 目标 |
|---|---|
| 人数 | 5–8 人 |
| 构成 | 在校生 / 应届生为主（实习生与校招岗），至少 2 人同时投 3 个以上岗位 |
| 前置条件 | 有一份自己的真实简历；**带一个自己真正在投的岗位 JD** |
| 排除 | 本项目的开发者、设计者、测试人员 |
| 时长 | 每人 60–75 分钟 |
| 形式 | 一对一，出声思维（think aloud），录屏 + 记录员 |

## 三、招募脚本（发给人选的第一条消息）

```

2）一个你正在投、或者最近打算投的岗位 JD（复制文字即可）。
```

## 四、任务脚本

### 任务 0 · 冷启动（观察首用三动作）
> 打开首页，不做任何引导。**「你现在会做什么？」**

记录：视线第一个落点；是否找到唯一主线；有没有被次级入口分散。

### 任务 1 · 建档
> 用你自己的简历建一份档案。

若解析失败或没配模型：**不要提示**，观察他会不会自己找到出口。

记录：是否看到「粘贴简历文字」；是否理解「不调用模型也能用」。

### 任务 2 · 加岗位 + 生成岗位版
> 加上你带来的那个 JD，生成一份针对它的简历。

记录：是否理解「岗位版 ≠ 母版」；改了岗位版后会不会担心母版被改。

### 任务 3 · 事实核对（**最关键**）
> 看看这份简历里哪些内容是已经确认过的。

**追问（必问）**
- 「系统有没有帮你确认过任何一条事实？」（正确答案：没有。系统只呈现，确认必须由人来做）
- 「这一条标着『待核对』，你觉得是什么意思？」
- 「如果你就这样导出，你觉得里面会有没经过你确认的内容吗？」

记录：是否把「系统提取到」误认为「已核实」；是否理解「采用改写」不等于「核实事实」。

### 任务 4 · 草稿 vs 正式投递版
> 导出一份准备发出去的简历。

记录：是否注意到草稿与正式版的区别；看到 PDF 上的 DRAFT 水印时是否理解其含义；文件名是否让他有信心发出去。

**追问**：「如果你不小心把草稿发出去了，你会怎么发现？」

### 任务 5 · 多岗位
> 再加两个岗位，各生成一份。然后把其中一份简历里的某个事实改掉。

记录：改完后是否期待另外两份跟着变；看到「关联了 N 份，其中 M 份可能需要更新」时的反应；是否敢点「只更新这一份」。

### 任务 6 · 面试准备
> 假设你已经把第一份投出去了，现在要准备它的面试。打开面试准备。

记录：是否注意到用的是「投出去的那一版」；如果产品说「尚无正式投递版本，当前使用准备中的简历」，他是否理解。

### 任务 7 · 恢复
> （当场清掉浏览器存储）刷新页面，把你的档案找回来。

记录：是否找得到恢复入口；是否以为数据丢了。

## 六、分析与判定

- 每场结束后 24 小时内补齐记录，标注严重度；
- 跨场次合并同类问题，**按出现人数计数**（如「8 人中 5 人把『提取到』当成『已核实』」）；
- 阻断级问题（导致任务无法完成）必须在本轮修复后重测；
- 事实核对（任务 3）出现**任何**误解都算严重——这是本轮的核心主张，误判会直接导致用户发出未核实的内容。

## 七、伦理与数据

- 简历与 JD 仅用于当场测试，测试结束即删除；
- 不采集身份证号、家庭情况等网申敏感字段；
- 录屏不出现在任何对外材料；
- 记录里只用编号，不写姓名；
- 人选可随时中止，数据当场销毁。
