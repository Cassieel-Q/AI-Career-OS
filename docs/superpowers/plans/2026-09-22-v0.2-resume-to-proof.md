# AI Career OS v0.2 Resume-to-Proof Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add one evidence-grounded Target JD → Target Resume → Claim Check → Interview Stress Test → Gap Diagnosis → Proof Action → Re-evaluation vertical slice on top of the existing P0 Completion Sprint.

**Architecture:** Keep the v0.1 Profile, JD, evidence, market, gap, priority, roadmap, fingerprint, invalidation, and provider boundaries intact. Add a small v0.2 proof domain for a profile-scoped target job, resume claims, interview sessions/turns, proof actions, and submitted artifacts; use bounded JSON fields for provider projections instead of duplicating the existing market tables. The new flow is a parallel step-by-step wizard that reuses UIX-001 shell styles and server rehydration patterns while the old Market/Priority/Roadmap routes remain available as a legacy flow.

**Tech Stack:** FastAPI, SQLAlchemy, Alembic, PostgreSQL/Supabase, Pydantic strict models, OpenAI-compatible `chat.completions.create` with explicit `response_format={"type":"json_object"}`, Next.js 15, React, TypeScript, Node test runner.

- `gap_service.py`, `priority_service.py`, `roadmap_service.py`, `derived_state.py`, and migrations through `008_p0_completion_sprint` remain the old planning loop and invalidation implementation.

- `workflow-shell.tsx`, `workflow-route.tsx`, `workflow-state.ts`, `workflow-navigation.ts`, and the existing route tests provide server-backed step navigation, refresh restoration, guards, retry states, and narrow viewport styles.

### B. Rename/reframe

- Reframe the start copy and new navigation around “I have a job in mind” and “what I would change / what I would not let you claim yet”.
- Reframe Gap/priority language in the new flow around JD importance, gap severity, goal relevance, actionability, and evidence confidence; do not expose raw `proximity`, `severity`, or `feasibility` enums as the primary user explanation.
- Treat the current Market Profile as optional confidence enhancement in v0.2; it is not the entry gate.

### C. Add

- Profile-scoped `TargetJob` record for one required JD, independent of the legacy `TargetRole`/three-JD market path.
- `ResumeClaim` records with current/suggested text, rationale, JD relevance, matched capability projection, evidence references, readiness (`SUPPORTED`, `DEFENDABLE`, `WEAK_EVIDENCE`, `UNSUPPORTED`), confidence, risk reason, and bounded attack-surface JSON.
- `InterviewSession` and `InterviewTurn` records for 3–5 adaptive text rounds, claim/JD/evidence grounding, and debrief fields with `KNOWLEDGE_GAP`, `PROJECT_GAP`, `EVIDENCE_GAP`, and `ARTICULATION_GAP`.
- `ProofAction` and `ProofArtifact` records for 1–3 artifact-producing actions and URL/text/manual evidence submission, followed by claim re-evaluation.
- A local AI Product Manager skill pack with the ten curated skill structures required by the product brief.
- Strict claim/interview/action provider adapters using the existing DeepSeek-compatible JSON transport pattern.
- `evals/` with five seed cases and human expected-output comparison metrics.

### D. Retain outside the new main flow

- Existing `/workflow/[profileId]/market-profile`, `/gap-analysis`, `/priorities`, `/roadmap`, `/progress`, and `/dashboard` routes and their persistence remain available for existing P0 data.
- Existing `TargetRole`, multi-JD collection, deterministic Market Profile, factor-based priority ordering, and four-week Roadmap stay untouched unless a focused compatibility fix is required.
- Existing profile confirmation remains the only operation that promotes a draft Profile to confirmed facts.

### E. Minimal DB migration

Create one forward-only migration `009_v0_2_resume_to_proof.py`; never rewrite `008`. Add six profile-scoped tables with UUID primary keys, explicit foreign keys, cascade only from the owning profile/job/claim/session, timestamps, bounded text, and uniqueness for one current target job per profile hash where appropriate:

1. `target_jobs`: profile, raw JD, source URL, content hash, status, and bounded JSON requirement/capability projection.
2. `resume_claims`: target job/profile, current/suggested claim text, explanation, readiness, confidence, risk, evidence refs, matched capability JSON, and attack surface JSON.
3. `interview_sessions`: claim/job/profile, status, round count, debrief gap type/why/evidence/next action, and summary JSON.
4. `interview_turns`: session, round number, skill id, question, answer, evaluation JSON, and follow-up dimensions JSON.
5. `proof_actions`: claim/session/profile, required action fields, status, and completion metadata.
6. `proof_artifacts`: action/claim/profile, artifact type, URL/text, user-confirmed evidence JSON, and submission timestamp.

The existing child Profile tables remain the source for profile evidence. Artifact evidence is additive and is included in the claim fingerprint; no pre-fix Profile/JD rows need rewriting or backfill.

### F. New API contract

- `POST /api/v1/profiles/{profile_id}/target-jobs` and `GET /api/v1/profiles/{profile_id}/target-jobs` — create/list one or more target jobs; one current job is selected for the new flow.
- `GET /api/v1/target-jobs/{target_job_id}` — read the bounded JD context and current claim state.
- `POST /api/v1/target-jobs/{target_job_id}/claim-analysis` and `GET .../claim-analysis` — generate/read strict evidence-grounded claim suggestions and readiness.
- `POST /api/v1/resume-claims/{claim_id}/interview-sessions` and `GET /api/v1/interview-sessions/{session_id}` — start a grounded stress test and read its debrief state.
- `POST /api/v1/interview-sessions/{session_id}/turns` — submit one answer and receive the next adaptive question or a completed debrief; enforce 3–5 rounds.
- `POST /api/v1/resume-claims/{claim_id}/proof-actions` and `GET .../proof-actions` — create/read 1–3 minimal artifact-producing actions.
- `POST /api/v1/proof-actions/{action_id}/artifacts` — submit URL/text/GitHub/report/manual evidence.
- `POST /api/v1/resume-claims/{claim_id}/re-evaluate` — re-bind profile/artifact evidence and return BEFORE/AFTER readiness.
